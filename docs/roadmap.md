# Vela 开发路线

这份文档说明**每一期做什么、什么推到下一期、什么永久不做**。判断某个功能该不该现在动手时，先查这里。

## 第一期（已完成）

单 Agent 的看板：六列 Board、建改删卡、拖拽排序、真实派活、Gate 验收、失败重试、token 用量、单卡执行配置、Workspace 筛选、批量建卡、从会话里提取待办。

### 一期里收尾时补上的两件

**越界写入真的会被拒绝（已真跑验证）。** 只读档位下 Agent 调了写文件工具，权限层回 `FS_SANDBOX_DENIED`，文件没被建出来。三件事同时成立才算通过——只看「文件不存在」不够，Agent 也可能自己决定不写，那时沙箱压根没被考验。

**会话内的一键提取待办。** 挂在会话头部，把讨论里的清单行摆成候选让 Operator 勾选，建卡时自动带上那个会话的工作目录。提取不自动建卡：建卡权归 Operator（ADR-0012）。【未验】按钮在真实界面里可见并可点这一条没有端到端点过，只有单元测试与源码取证支撑。

## 第二期（已完成）

把 Multica 的形状补齐，并把「多 Agent」从一个 Agent 变成一支小队。

- **Squad** — 队长 + 队员，各自的 Instruction，队员各自的工具白名单，Squad 级沙箱档位
- **并发硬闸门** — 看板级 Run 上限 + 每个 Squad 的 Delegation Slot（ADR-0018）
- **Squad 并行时间轴** — 谁在什么时候跑；单会话轨迹跳去 DSH（ADR-0019）
- **Issue 详情抽屉** — 右侧滑出，含历次 Run 记录与时间轴（ADR-0020）
- **任务编号** — 卡片有稳定可引用的编号
- **泳道配色** — 六列各有辨识度，日间夜间都成立
- **Squad / Preset 选择器** — 派活时选用哪支队伍
- **看板内搜索** — 按编号 / 标题 / 描述找卡；找历史会话交给 DSH
- **左侧导航映射** — Multica 的三组十二项，按 ADR-0020 的归属表落位

### 二期里被实跑推翻的三个设计

这三条都是先写进 ADR、再被一次真实派活推翻的。它们留在这里是因为**改回去就会静默坑掉功能**：

**小队的组合必须建在基准 preset 之上。** 一份 preset 是 agent 平面的完整组合，不是补丁。从零写的组合会取代 `standard`，队长手里连 `read` 都没有（ADR-0016）。

**队员必须是一次性模式。** 可继续模式把委派默认变成后台，而后台可继续子代理不经过 provider 的起跑路径——号牌闸门因此完全失效（ADR-0018）。

**时间轴的时刻不能靠监 `subagent/start` 事件。** 那个事件的载荷里没有父会话 id，第三方拿不到。改在号牌 provider 的起跑路径上打（ADR-0019）。

### 二期里没做到、已记在票里的几件小事

- 详情抽屉关闭后焦点回到 body 而不是原卡片
- 「中途取消」与「队长报错时卡片进失败」靠的是单元测试，不是真跑
- 配色的截图留证没交付（自动化截图在这个环境里超时），替代证据是真实计算色值与一张可自开的样张
- 可继续子代理那条路上号牌拦不住（那条路没有结束信号，领牌必然漏还）
- 时间轴不落盘，进程重启后消失

## 第三期（下一期）

以下功能**本期刻意不做**，界面上以灰色占位标注「下一期」，不是遗漏。

### Autopilots（自动化）

按规则自动派活，例如「卡片进 Todo 就自动开跑」「失败自动重试一次」。

推后的理由：自动派活会绕过 Operator 的判断，而现在连「Operator 手动派活会不会撞并发上限」这件事都还没跑够。自动化应该建立在一套已经稳定的手动流程上。

### Projects（项目实体）

比 Workspace 更粗的一层归组，一个 Project 下可以有多个 Workspace 的卡。

推后的理由：Workspace 已经能承担绝大多数归组需求（ADR-0001 明确 Workspace 不是多租户边界）。再加一层要先有真实的痛点，否则只是多一个必填字段。

### Usage（用量汇总）

跨卡、跨 Squad、按时间段的 token 与花费统计。

推后的理由：单卡的用量快照第一期已经有了（ADR-0011）。汇总视图的价值取决于攒够多少数据，现在做出来是一张空表。

### 截止日期

给卡设 due date 并在临期时提示。

推后的理由：Vela 目前没有任何时间驱动的机制。加日期就得加提醒，加提醒就得决定提醒去哪——这条链的第一环还没有。

### 列表视图与表格视图

Multica 有五种视图模式，Vela 目前只有看板一种。

推后的理由：看板是 Board 之所以叫 Board 的原因（ADR-0005）。另外几种视图是同一批数据的不同排布，等数据量真的大到看板装不下再说。

### Codex / Claude Code 作为 Member

让一支 Squad 里混编 DSH 自己的 agent 与外部 CLI。

推后的理由不止是工作量：这类 Member 的后端能力标记里工具白名单与 Instruction 都是 `false`，所以它们**拿不到**自己的职责说明和限权（ADR-0017）。现在做出来只能是一个既不能限权也不能定职责的队员。等 DSH 那边支持了再做。

## 永久不做

以下不是推迟，是**已经决定不做**，有 ADR 记录。要重开必须先推翻对应的 ADR。

| 不做的事 | 理由 | 出处 |
|---|---|---|
| 人的成员、角色、访问权限 | DSH 全库没有身份体系，且 Web 服务只绑本地回环 | ADR-0001 |
| Agent 自己往 Board 上写卡 | 建卡权归 Operator，否则 Board 变成 agent 的草稿本 | ADR-0012 |
| 可配置的 Lane | 六列是状态机，不是视图偏好 | ADR-0009 |
| Gate 承担操作审批 | Gate 是产出验收，异步可积压；审批是同步阻塞 | ADR-0008 |
| Run 成功后直接进 Done | 成功只到「待验收」，Done 只能由 Operator 给 | ADR-0007 |
