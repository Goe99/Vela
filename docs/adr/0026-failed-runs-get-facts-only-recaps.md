# 失败与中断的 Run 只落客观 Recap，且不参与 Recall

失败、超时、被取消、以及对账出来的中断执行同样落一篇 Recap，但**只落 Vela 自己数得出来的部分**：碰过哪些文件、跑过哪些命令、报了什么错、用量与耗时。不放 Agent 的收尾正文，也不参与 Recall——只在 Operator 打开那张卡时给他看。

理由是一条既有的状态事实：失败的卡不进「待验收」，因此它的 Recap 永远等不到人来审，会永久停在 unverified。若让 unverified 的东西参与 Recall，Trust Level 就不再有意义；若干脆不落盘，就丢掉了「上次在这个文件上撞了同一个错」这类最便宜也最可靠的事实。

## Considered Options

- **只有成功的执行落 Recap** — 拒绝。最干净，但丢掉了「这条路走不通」这类最贵的经验。
- **给 Failed 卡也开一个验收动作，让失败的 Recap 也能审** — 拒绝。ADR-0007 刻意只让「待验收」有出口，多开一个入口就多一套状态要解释，而失败执行的收尾回复常常只有半句话或根本没有（超时、被杀），审它审不出什么。
- **失败的 Recap 参与 Recall，只是排序靠后** — 拒绝。那等于悄悄把没人审过的东西喂进下一次执行，正是这个模块要防的事。

## Consequences

客观部分无需任何人审就能显示给 Operator，因为它不是模型说的，是 Vela 从会话事件里数出来的。

Recall 的候选集因此只有一种来源：**经 Gate 接受过的 Recap**。「注入的东西凭什么可信」有了一句话答案。代价是待验收积压期间那篇 Recap 也不参与 Recall——积压是 Operator 自己的节奏，Vela 不替他提前采信。
