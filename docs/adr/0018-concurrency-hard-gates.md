# 并发是两道硬闸门，都由 Vela 自己把守

Vela 不靠劝模型来控制并发。两个不同层级各有一道真闸门：

**看板级 — 同时在跑的 Run 有数量上限。** 派活前清点，跑满了就**拒绝这次派活**并告诉 Operator 原因。

**Member 级 — 每个 Squad 持有固定数量的 Delegation Slot。** Vela 注册自己的委派后端，包在 DSH 的 spawn / fork 外面（名字加 `vela-` 前缀）：Member 起跑前必须领到一个 Slot，领不到就在后端里**排队等**，结束时交还。

为了让这道闸门真的盖住所有路径，Member 必须配为 **一次性模式**（`backgroundMode: one-shot`）。原因与实跑证据见下文。

两道闸门的处置方式**故意不同**，理由见下。

## 看板级为什么是拒绝，而不是排队

排队需要一个「排队中」的状态，而 ADR-0009 把六条 Lane 钉死了。一张卡停在 Todo 却其实已经在等着起跑，是个**看不见的状态**——Operator 看着 Board 会以为自己忘了点派活。一条明确的「当前已有 3 个在跑，等一个结束再派」比一个隐藏状态诚实得多。

## Member 级为什么排队是对的

Leader 眼里，一个排队中的 Member 只是「这个工具慢了点」——委派工具本来就可能耗时，等待不产生任何新状态，也没有任何东西对 Operator 隐身。同一件事在两层得出相反结论，是因为两层的观察者不同：Board 的观察者是人，委派工具的观察者是模型。

**刻意不告诉 Leader 它被限流了。** 告诉模型「你被限流了」只会让它开始揣测和绕路——改成串行、或者把五个任务塞进一次委派。让它以为工具就是这个速度，行为最可预测。

## 为什么不用 DSH 自带的那个并行上限

DSH 有 `maxParallelToolCalls`（`agent-loop` 命名空间下的用户设置，默认 10），能通过我们已经在用的设置网关改。两个毛病，都是致命的：

- **它是全进程的。** 调低它会连 Operator 自己聊天时的工具并行度一起限。
- **它数不到后台的 Member。** Member 以可继续后台模式起跑时，委派工具**立刻返回**一个子会话 id，Member 在外面继续跑。工具调用早就结束了，这个上限根本不参与。

## 自己注册后端是文档许可的，不是钻空子

`ctx.subagents.registerProvider(provider)` 是公开方法并返回 disposer。DSH 的后端合约里两处明确写了容量排队是预期用法：「a shared capacity controller may delay an operation but must not couple its settlement or cleanup to a sibling」，以及「A provider may queue its own capacity internally without changing that independence contract」。

## Considered Options

- **只把并发数写进 Leader 的 Instruction，劝它自律** — 拒绝。模型不遵守时 Operator 无从得知，而后果是撞限流导致一批 Member 连带失败；按 ADR-0009 的规则那些失败又不改卡的落位，于是 Board 上会出现一张「成功」的卡里躺着五个红叉，极难排查。
- **把 Member 全改成前台一次性模式，借工具并行上限硬拦** — **部分拒绝，部分被实跑推翻**（见下节）。拒绝的那半仍然成立：不靠 `maxParallelToolCalls`，因为它是全进程的。但「一次性模式」本身是必需的。

## 实跑推翻了什么：队员必须是一次性模式

第一版把队员配成 `backgroundMode: continuable`（理由写在 ADR-0016：队员会话可回访、可补充指令）。一次真跑把它否了：队长的三次委派**全部**走了后台可继续路径（工具结果是秒回的 `started subagent <id>`），号牌一次也没参与。

机理：`continuable` 把委派的**默认**变成后台，而后台可继续子代理的整个生命周期归 DSH 的 continuation manager，provider 只贡献一份创建规格——**不经过 `provider.start()`**。号牌就括在 `start()` 里，那条路上它不存在。

一次性模式下两条路都过 `start()`：前台直接调，后台经 `jobs.start()` 也调。因此闸门完整覆盖。

**当时写进拒绝理由的那两个代价，一个真一个假。** 真的：队员不能再续聊（但依旧能点进去看，会话本身是真存在的）。假的：「Leader 每次委派都被阻塞」——实跑里模型在同一毫秒内并行发起了三次前台委派，工具并行调用本来就允许。阻塞的是那三个调用各自的结果，不是队长本身。

## 实跑证据

一支只有**一张**号牌、但有三个队员的队，一张要求同时做三件事的卡。

队长在同一毫秒内发起了三次委派（发起时刻 0 / 0 / 1）。三个子代理**自己会话**的区间：

```text
创建 slot-a.txt   [0,    2356]
创建 slot-c.txt   [2357, 5125]
创建 slot-b.txt   [5127, 7778]
```

完美串行，衔接间隔 1–2ms（正是还牌转手的延迟）。号牌没生效的话三个区间会全部从 0 开始重叠。三个文件都建出来了——排队不等于丢活。

### 一个关于量尺的教训

头两轮验证拿错了尺子：看队长会话里 `tool/call` → `tool/result` 的区间。无论后台可继续还是后台 job，工具都是秒回的，区间长度与队员实际跑了多久无关。更阴的是第一轮：解析器没匹配上任何结束时刻，于是重叠判定被整体跳过，报告出了一个看起来像成功的「重叠 0」。

因此任何「无重叠」的结论都必须伴随「真的量到了几个区间」。正确的尺子是问 dsh 要子代理清单，再读每个子代理自己会话的首末事件时刻。

## Consequences

**Vela 从此有一个被 DSH 调用的后端。** 这是新增的一份对外契约，能力标记必须逐字对齐所包的 spawn，否则 Member 行会在挂载时被能力校验拒掉——而挂载失败等于整个 Squad 起不来（ADR-0016）。

**Slot 的交还路径必须幂等，且要有兜底。** 漏还一个 Slot 会**永久**缩小该 Squad 的并发能力，且症状是「越用越慢」这种最难查的形态。因此结束事件之外必须有超时对账，这是必需项而不是加分项。

**进程重启后可能短暂超额。** 号牌活在内存里，不落盘。重启后上一轮还在跑的队员（如果有）不占号牌，因此短时间内实际并发可能超过设定。本地自用可接受；记录在此以免日后当成 bug 追查。

**可继续路径上号牌无法生效，这个限制是永久的。** `prepareContinuable` 只贡献一份创建规格，provider 之后既收不到结束信号也没有 handle。在那条路上领牌等于**必然漏还**，而漏还比少拦一条路更糟。因此那个方法只转发不领牌。这也是队员必须保持一次性模式的原因——改回 `continuable` 会让整道闸门静默失效。

**两个上限都得能改，且都有默认值。** 看板级的上限是全局设置，Member 级的 Slot 数量属于每个 Squad 自己——因为不同 Squad 的队员数量和烧钱速度差别很大。
