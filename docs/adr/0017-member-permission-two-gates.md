# Member 的权限只有两层闸门，且永远不会弹审批

一个 Member 实际能做什么，由**恰好两件事**决定：

1. **Squad 的沙箱档位** — 施加在 Leader 会话上，DSH 在委派那一刻快照给 Member
2. **该 Member 的工具白名单** — 写在它那一行的 `toolFilter`

没有第三层。尤其**没有审批**：Vela 不提供、也不假装提供「Member 干某件事之前先问我一句」。

## 审批被 DSH 钉死了

委派边界上，DSH 捕获父会话的策略交给子代理时，把审批策略**固定写成 `'never'`**——只要审批能力在组合里就一定是这个值。官方给的理由是：受委派的子代理只在委派时固定下来的沙箱范围内行动，所以它的请求被确定性地拒绝。

后果必须说清楚：**Member 碰到需要确认的操作不是「等你点」，而是「直接被拒」。** 所以给一个 Member 配一件需要审批才能做的事，等于配了一件它做不到的事——它会拿到一个失败的工具结果，然后自己想别的办法或者放弃。

这也意味着沙箱档位在小队场景下的分量比单 Agent 场景重得多：单 Agent 跑得太野时，审批还能拦一下；Member 没有这道网。

## 沙箱是委派瞬间的快照

Leader 会话在委派**之后**改档位，不影响已经起跑的 Member。因此 Vela 必须在提交任务之前把档位施加好——Runner 现有的顺序（建会话 → 施加档位 → 改名 → 提交任务）本来就满足，本 ADR 把这个顺序从「碰巧对」升级为「必须如此」。

## 白名单必须走受控选项

白名单里出现一个不存在的工具名，会让**整个 Squad 挂载失败**——那个 Squad 的会话根本建不起来。让 Operator 手打工具名就是把一个 fail-loud 的地雷埋在最常走的路径上。

所以默认路径是**勾选粗粒度能力组**（读文件 / 改文件 / 跑命令 / 联网 / 再派下一级），由 Vela 把每组映射到一份硬编码的工具名清单，并用测试锁住这份映射。自由填工具名保留在「高级」折叠区里，给知道自己在干什么的时候用。

## Considered Options

- **给每个 Member 单独设沙箱档位** — 拒绝，因为**没有这个接缝**。委派只捕获父会话的沙箱覆盖，DSH 里不存在「按子代理指定档位」的机制。要做只能给每个 Member 单起一个顶层会话，那就不是小队了。
- **让 Member 的审批冒泡给 Operator** — 拒绝。DSH 钉死为 never，插件改不了；退一步说，就算能改，一个跑十个 Member 的 Squad 会把 Operator 变成人肉审批队列，与 ADR-0008「Gate 是产出验收，不是操作审批」的立场直接冲突。
- **白名单默认自由填工具名** — 拒绝，理由见上：默认路径不该埋 fail-loud 地雷。

## Consequences

Squad 编辑器里，沙箱档位是 **Squad 级**的一个选择，工具白名单是 **Member 级**的多个选择——两者层级不同，界面上不能摆成同一排，否则会误导。

外部产品后端（Codex / Claude Code）的能力标记里 `toolFilter` 与 `persona` 都是 `false`，因此这类 Member **拿不到**自己的 Instruction 和白名单。这是把它们推到下一期的主要理由（见 `docs/roadmap.md`）：现在做出来只能是一个既不能限权、也不能定职责的队员。

「最小权限」在 Vela 里的完整表述因此收敛为：**Squad 决定这次执行能碰多大范围，Member 决定它在这个范围里能用哪几把工具。** ADR-0001 说的「主体从团队成员换成 Agent」到这里才算真正落地。
