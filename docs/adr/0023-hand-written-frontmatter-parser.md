# 自己写 frontmatter 解析，不引 YAML 库

`core/okf` 里自写一个只认受控子集的 frontmatter 解析与序列化：标量（字符串与数字）、标量数组、一层深的对象（`generated`）、以及一层深对象的数组（`verified` / `sources`）。**不认识的键原样保留并回写**（OKF 要求消费者容忍未知字段，丢掉它们就等于悄悄改坏别人的文件）。解析失败必须报出是哪一行、哪个键，不静默跳过。

受控子集按**形状**而非按字段名定义（不是「只认 `sources` 与 `verified`」）：形状无关乎键叫什么，因此别人知识包里同形状的自定义键也能读得懂——而认字段名会把它们读成错误。

理由是范围：这些文件由 Vela 自己写、自己读，形状完全受控，需要的表达力远小于一个 YAML 库能提供的。而领域层至今零第三方依赖，是 Vela 能脱离宿主单测的原因。

## Considered Options

- **引 `js-yaml` 或 `yaml`** — 拒绝。dsh 虽然捆绑了一份 `js-yaml`（测试里 require 得到），但那是宿主的内部依赖，production 里 Vela 得自己装一份，于是插件体积、版本漂移、以及「第三方插件带自己的依赖树」这些代价全要自己背——换来的只是解析一段十来行的固定 frontmatter。
- **改用 JSON frontmatter** — 拒绝。省掉解析问题，但同时脱离 OKF，人手改文件的体验也变差（引号、逗号、不能写注释）。规范合规是这个模块存在的理由之一，不能拿它换省事。

## Consequences

解析器只保证读得懂 Vela 自己写出来的形状。人手改坏的文件要**报错**而不是猜——一篇解析不了的 Recap 应当在界面上显示成「这篇读不了」，而不是从列表里消失。

反悔条件写在这里，省得下一个人重新论证：一旦需要支持人手写的嵌套结构（锚点、多行折叠、块标量、注释保留），就该换成库。那时要换掉的只有这一个文件。

## 实现后的补注

落实为 `src/domain/okf-frontmatter.ts`（不单开一层 `core/okf` 目录：现有领域层是平铺的，为三个文件新开一层只多一道跳转）。实现后派生出两条当时没想到、但很容易被“修好”成错的纪律，均有测试锁住：

- **形如数字的字符串必须带引号写出。** 否则 `title: "3"` 往返一轮就变成数字 3。
- **同一个键出现两次报错，而不是后者覆盖前者。** 覆盖是最坏的处置：文件里明明写着两个值，读出来只剩一个且没人知道。
