# Squad 的并行时间轴由 Vela 画，单会话轨迹交给 DSH

Vela 只画一件 DSH 画不出来的东西：**一个 Run 里各个 Member 谁在什么时候跑**。至于某个 Member 具体做了哪些步骤，Vela 一笔不画——每条泳道点一下，跳去 DSH 自己的轨迹界面看。

## DSH 的轨迹视图不能复用

`dsh-client-ui-trajectory` 是内部包，**没有对外导出任何组件或 hook**，插件 import 它会解析失败。这与 ADR-0015 里 headless 那三个值导入是同一个病根：包捆绑在全局安装内部，第三方插件的 Node 解析到不了。

所以「复用 DSH 的甘特图」在实现层面不成立。但**跳转**成立，而且跳过去看到的就是官方那份视图——比我们重做一份更好。

## 时间戳是我们自己打的

委派的开始与结束事件（`subagent/start` / `subagent/end`）**载荷里没有时间戳**：开始只带运行 id、后端名、子会话 id 和一个是否进程内的标记，结束多带一个停止原因和最后一条消息。

所以 Vela 在**收到事件的那一刻**自己打时间戳。这足够画时间轴，但必须诚实标注它是什么：**「Vela 观察到的时刻」，不是「Member 真正起跑的时刻」**。差值是事件派发的延迟，进程内可忽略，但这是近似值——不能拿它做性能归因。

## 分工的原则

Vela 画跨会话的**并行关系**，DSH 画单会话内的**步骤明细**。这条线之所以画在这里：并行关系是小队场景下唯一在别处看不到的信息，而步骤明细 DSH 已经做得很好。

## Considered Options

- **从子会话历史重算每个 Member 的完整步骤，自己画明细** — 拒绝。那是把 DSH 的轨迹视图重做一遍，且要跟着上游的事件形状变。
- **不画时间轴，只列每个 Member 的当前状态** — 拒绝。并行关系正是这一期要交付的东西；只给一份状态列表，Operator 依然看不出「这两个 Member 是不是同时在跑」。

## Consequences

时间轴**只在有 Squad 的 Run 上出现**。单 Agent 的 Run 里没有并行关系可画，那里直接给一个跳去 DSH 的按钮。

**事件订阅必须在进程启动时就装好。** 漏掉的开始事件无法追补——子会话本身能从历史里翻出来，但它的起跑时刻找不回来。这让「什么时候订阅」从实现细节变成了正确性要求。
