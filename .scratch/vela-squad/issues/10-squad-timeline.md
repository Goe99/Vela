# 10 — Squad 并行时间轴

**What to build:** 详情抽屉里出现一条时间轴，一眼看出这次执行里各个队员谁在什么时候跑、谁和谁重叠、谁失败了。每条泳道点一下，跳去 DSH 看那个队员自己的完整轨迹。

按 ADR-0019：Vela 只画跨会话的并行关系，单会话内的步骤明细一笔不画——那是 DSH 已经做得很好的部分。

**Blocked by:** 08 — 派活时选一支 Squad；04 — Issue 详情抽屉（时间轴的容器）

**Status:** done

- [x] 订阅在进程启动时就装好（ADR-0019：漏掉的起跑事件无法追补）
- [x] 每个队员一条泳道，横轴是时间，能看出重叠关系
- [x] 每条泳道显示队员名字、状态（在跑 / 完成 / 失败）、耗时
- [x] 失败的队员用配色区分，且能看到停止原因
- [x] 点一条泳道跳去 DSH 看那个队员的会话
- [x] 时间来源标注清楚是「Vela 观察到的时刻」，不是队员真正起跑的时刻（ADR-0019：这是近似值，不能拿去做性能归因）
- [x] 只在有小队的 Run 上出现；单 Agent 的 Run 里不画时间轴，直接给跳去 DSH 的按钮
- [x] 正在跑的 Run 上时间轴会增长；跑完后定格
- [x] 一个队员都没派出的小队 Run，给出明确空状态而不是一条空轴

## 完成记录

### 真跑证据

复用了号牌那支「一张号牌、三个队员」的队。三条泳道的实际区间：

```text
创建 tl-b.txt   [0,     7847]   worker_b   completed
创建 tl-a.txt   [7852, 15803]   worker_a   completed
创建 tl-c.txt   [15806, 22447]  worker_c   completed
```

串行、衔接 3–5ms，与号牌那次真跑观察到的结构一致——两层互相印证。三个队员名全部反查
成功，任务描述也都在。轮询过程如实显示了增长：2 条（含 1 个在跑）→ 3 条（含 1 个在跑）
→ 3 条全完。三个文件都建出来了，卡片进「待验收」。

### 时刻从哪里来：不是监事件，是在起跑路径上打

ADR-0019 原本写的是监 `subagent/start` / `subagent/end`。取证发现那两个事件的载荷里
**没有父会话 id**——它靠监听器的 `this` 传，而那是 dsh 内部的 carrier key，第三方拿不到。

改成在号牌 provider 的 `start()` 里打时刻：那里父 agent 直接在手，而且它天然只盖住走我们
后端的派生，也就是小队队员——正好是「只在有小队的 Run 上出现」那条要求。ADR-0019 的
结论没变（Vela 只画跨会话并行、单会话交给 DSH），变的是实现落点。

「订阅必须在进程启动时就装好」这条正确性要求同样满足：时间轴与号牌同处挂载，比任何
一次派活都早。

### 真跑抓到的一个真 bug

队员名第一次真跑**全部反查失败**。原因：我去读 `descriptor.persona`，而 one-shot 模式的
descriptor 快照里只有 version/mode/provider/label，**根本没有 persona**（只有 continuable 的
快照才带）。而队员必须是 one-shot（ADR-0018）。改成读请求根上的 `persona` 后全部命中。

### 队员名是尽力而为，任务描述才是主标签

DSH 给 provider 的请求里没有队员的工具名，只能靠职责说明反查。两种情况查不到就不猜：
队员没写职责，以及两个队员职责完全相同（那时它们本来就无法区分）。

这不是缺陷——任务描述（「创建 tl-a.txt」）比队员名（「worker_a」）信息量更大，dsh 自己的
子代理清单也是用它。

### 不落盘，这是有意的

时间轴与实时 token 用量同一套路（ADR-0011：在途状态不落盘）。ADR-0019 已经承认漏掉的
起跑事件无法追补，那么把一份残缺的观察持久化下来只会让人以为它是完整的。

代价：**进程重启后已有的时间轴会消失**，卡片与执行记录不受影响。
