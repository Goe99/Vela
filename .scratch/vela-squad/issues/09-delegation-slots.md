# 09 — Delegation Slot：队员并发的硬拦截

**What to build:** 每支小队手里有固定数量的号牌。队员起跑前必须领到一个，结束时交还；领不到就排队等。这不是写进队长职责说明里的劝告，而是队员**根本起不来**。

做法按 ADR-0018：Vela 注册自己的委派后端，包在 DSH 的 spawn 外面，号牌捏在这一层。队员配置里填我们这个后端。

**Blocked by:** 08 — 派活时选一支 Squad（要先有真的队员在跑）

**Status:** done

- [x] Vela 注册的委派后端能被 DSH 认出并正常派生队员，能力标记与所包的 spawn 逐字一致
- [x] 号牌数量取自该小队的设置
- [x] 真实验证：把号牌设成 1，让队长一次派三个队员，观察到它们**串行**起跑而不是同时
- [x] 排队中的队员对队长表现为「工具慢」，队长收不到任何「你被限流了」的信号
- [x] 队员结束时号牌交还，且交还路径幂等
- [x] 有超时兜底对账：即使结束事件没来，号牌最终也会被回收
- [x] 取消整个 Run 时，排队中还没起跑的队员被丢弃
- [x] 号牌逻辑有测试覆盖：满额排队、结束释放、重复释放、取消清空、超时回收
- [x] 进程重启后可能短暂超额这件事在完成记录里注明

## 完成记录

### 真跑证据

一支只有**一张**号牌、但有三个队员的队，一张要求同时做三件事的卡。

队长在同一毫秒内发起了三次委派（发起时刻 0 / 0 / 1）。三个子代理**自己会话**的区间：

```text
创建 slot-a.txt   [0,    2356]
创建 slot-c.txt   [2357, 5125]
创建 slot-b.txt   [5127, 7778]
```

完美串行，衔接间隔 1–2ms（正是还牌转手的延迟）。号牌没生效的话三个区间会全部从 0 开始重叠。三个文件都建出来了（排队不等于丢活），无任何委派报错。

### 为了让它生效，改掉了一个已写进 ADR 的选择

第一次真跑发现号牌**完全没参与**：队长的三次委派全走了后台可继续路径，而那条路的生命周期归 DSH 的 continuation manager，不经过 `provider.start()`。于是队员的 `backgroundMode` 从 `continuable` 改为 `one-shot`——一次性模式下前台与后台 job 两条路都过 `start()`。

代价与修正已写进 ADR-0016 与 ADR-0018。ADR-0018 里原本拒绝一次性模式的那条理由，一半是错的：「队长每次委派都被阻塞」——实跑里模型并行发起了三次前台委派。

### 一个关于量尺的教训

头两轮验证拿错了尺子：看队长会话里 `tool/call` → `tool/result` 的区间。无论后台可继续还是后台 job，工具都是秒回的。更阴的是第一轮：解析器没匹配上任何结束时刻，于是重叠判定被整体跳过，报告出了一个看起来像成功的「重叠 0」。现在的报告会连带输出「真的量到了几个区间」。

### 测试抓到的一个真 bug

`prepareContinuable` 的**有无**是 DSH 判断「这个后端支不支持可继续子代理」的依据。写成类方法则 `delete` 删不掉；改成可选类字段则 `useDefineForClassFields` 会把它定义成 `undefined`，`in` 照样为真。两种写法都会向 DSH 谎称支持，然后在真的被调时失败。最终改成工厂函数 + 对象字面量的条件展开，让「有这个键」与「支持这件事」变成同一回事。

### 两个诚实记下的限制

**可继续路径上号牌无法生效，而且这是永久的。** `prepareContinuable` 只贡献一份创建规格，provider 之后既收不到结束信号也没有 handle，领牌等于必然漏还。因此那个方法只转发不领牌。这也是队员必须保持一次性模式的原因。

**进程重启后可能短暂超额。** 号牌活在内存里不落盘，重启后上一轮还在跑的队员不占号牌。本地自用可接受。

### 取消那一条靠的是测试，不是真跑

「取消整个 Run 时丢弃排队中的队员」有完整的单元测试（含「取消后即使有人还牌，已取消的队员也不会起跑」这条），但没有真跑验证——需要正好卡在队员排队的窗口里发出取消，很难自动化到可靠。
